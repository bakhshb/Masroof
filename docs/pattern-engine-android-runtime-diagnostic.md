## 2. Why JVM tests passed and Android runtime failed

Static analysis of the final clean debug APK:

- **All 80 top-level `com.baraa.masroof.sms` + `com.baraa.masroof.transaction`
  classes are packaged** in the dex set (verified via dexdump class
  descriptor list).
- **All nested classes referenced by `MessageTemplateEngine.buildFromSms`
  are packaged** (`CanonicalMessageNormalizer$CanonicalLine`,
  `$CanonicalMessageStructure`, `$ParsedTemplateLine`, `$ValueToken`,
  `SemanticPatternCanonicalizer$Fingerprint`, `$CoreSlot`, `$OptionalSlot`,
  `MessageTypeCueCatalog$Rule`, etc.).
- **All file-facade classes for files with top-level declarations are
  packaged** (`SemanticPatternSchemaKt`, `CanonicalMessageNormalizerKt`).
- The transitive import set of the `buildFromSms` chain is exclusively:
  - `java.util.regex.Pattern`, `java.util.Locale`, `java.text.Normalizer`,
    `java.math.BigDecimal`, `java.security.MessageDigest`,
    `java.time.{LocalDate,LocalTime,LocalDateTime}`,
    `java.lang.{String,Object,Enum,Integer,Iterable,Long,RuntimeException}`,
    `java.util.{List,Map,Set,Comparator,function,stream,concurrent,…}`.
  - `kotlin.text.Regex`, `kotlin.collections.*`, `kotlin.jvm.internal.*`.
  - No `kotlinx.serialization`, no third-party library reference.
- A cross-dex scan (`comm -23 referenced defined`, filtered to
  `Lcom/baraa/masroof/`) found **zero app classes referenced but undefined
  in any dex** in the buildFromSms dex.
- `apkSHA256=10ec3a1c1a5609ab5a018609fa616990af9045200e1ed8b56fbe900ae2b3b8f9`
  (debug). `0f1cf5f6b189b75bc005d91c459844d63db71c96a5e3e8ed9ceb2359e0f0c316`
  (androidTest).

**No app class is missing from the APK.** Since TYPE_CUE (which uses
`BankSmsFilter`, `MessageTypeCueCatalog`, `SmsStructureNormalizer`,
`java.text.Normalizer`) succeeds on the device but TEMPLATE_BUILD (which
additionally uses `CanonicalPatternFieldClassifier`, `MonetaryFieldClassifier`,
`CanonicalMessageNormalizer`, `LineBasedFieldParser`, `BankTextNormalizer`,
`SemanticPatternCanonicalizer`) fails with `NoClassDefFoundError`, the most
likely cause is a **static-initializer (`<clinit>`) failure** on Android
for one of the TEMPLATE_BUILD-only objects. A failed `<clinit>` marks the
class as `Erroneous`; subsequent references throw `NoClassDefFoundError`
whose `message` is the class FQN — exactly what the diagnostic captures.

Plausible culprits to inspect on-device (the diagnostic will name the one):
- A `Regex` pattern in `LineBasedFieldParser` or `MessageTemplateEngine`
  whose compilation throws `PatternSyntaxException` on Android's
  `java.util.regex` (ICU) engine even though it compiles on the JVM.
- A `<clinit>` referencing a class that is loaded on the JVM but is not
  available at Android runtime (a class the static analyzer could not
  see because the reference is generated by the Kotlin compiler).

The diagnostic surfaces the exact class on the next device run.

## Resolution

The on-device diagnostic captured:

- **Missing/erroneous class:** `com.baraa.masroof.sms.PatternStructure`
- **Root cause:** `ExceptionInInitializerError: PatternSyntaxException: Syntax
  error in regexp pattern near index 11`
- **First relevant frame:** `CanonicalMessageNormalizer.normalizeParsed`
  (kt:140) → `normalizeFromLines` (kt:131) → `normalizeBody` (kt:86)

Android's `java.util.regex` (ICU) rejects the regex

```kotlin
private val PLACEHOLDER = Regex("""\{([^{}]+)}""")
```

because the trailing bare `}` (index 10) is not a valid brace outside a
quantifier on the device runtime (JVM tolerates it; Android ICU does not).
`PatternStructure` is loaded for the first time from
`CanonicalMessageNormalizer.normalizeParsed` → `PatternStructure
.isOptionalContextAnchor(...)` (the only call path that first touches
`PatternStructure` in `buildFromSms`). The failed `<clinit>` marks the
class as `Erroneous`; the first SMS throws `ExceptionInInitializerError`,
every subsequent SMS throws `NoClassDefFoundError` — matching the observed
"196 / NoClassDefFoundError" stream.

### Fix

Escape the trailing `}` so the pattern compiles on both engines (the
matched language is unchanged):

```kotlin
// PatternStructure.kt
private val PLACEHOLDER = Regex("""\{([^{}]+)\}""")     // was: }""")
```

The same non-portable regex existed as a latent bug in
`TemplateEditValidator.placeholderPattern` (`TemplateEditorModels.kt`).
It was not loaded by discovery (so it did not crash the current flow)
but would have crashed the moment the user opened the template editor on
the device. Fixed identically:

```kotlin
// TemplateEditorModels.kt
private val placeholderPattern = Regex("""\{([^{}]+)\}""")  // was: }""")
```

Other placeholder regexes were already portable
(`CanonicalMessageNormalizer.PLACEHOLDER_REGEX` and
`TemplateMatcher.PLACEHOLDER` both already escaped the closing brace).
